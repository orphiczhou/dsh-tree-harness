## 1. 流程总览

每个 Sprint（≤2 周，见 `sprint-plan.md`）内编程Agent团队按以下六步流水线执行（对齐需求源 §6.2 与 §11.5，角色编号见 `team-config.md`）：

```
Sprint 工作包（来自 sprint-plan.md §3 + PM P8 排程）
   │
   ▼
① 架构师审核规约（P1）───────── 失败 → 规约问题单 → P1 裁决/走变更流程
   │ 通过：开工许可
   ▼
② 前端 + 后端并行开发（P2 ∥ P3）─ 失败 → §4 异常自愈流程
   │  前端：原型 HTML 为 UI 模板 + Mock 数据（不阻塞后端）
   │  后端：引擎模块 + E-xx 端点
   ▼
③ 前后端联调（P2 + P3）───────── 失败 → 缺陷定位 → 回 ② 局部修复（入自愈计数）
   │ 联调通过：可运行增量
   ▼
④ 代码审查（P6）─────────────── 失败 → change requests → 回 ②/③ 修复 → 重审
   │ approve
   ▼
⑤ 测试Agent 执行 GWT（P5）────── 失败 → 失败场景清单退回 ②/③ → 先重跑失败场景再全量回归
   │ 89 条口径相关子集 100%
   ▼
⑥ 裁判校验（M5 JudgeEngine）──── 失败 → 退回单（缺项清单）→ 回 ②/③ 修复 → 重走 ⑤⑥
   │ 通过（长期型不限退回次数，必须通过）
   ▼
合并 + Sprint 收口（P8 登记，M2 追加 changelog）→ 下一 Sprint
```

**两点总原则**：
1. **引擎间不互相调用，一切交接走文件**（ADR-05）：各步之间交接介质一律为项目目录中的文件产物（`.md`/`.prototype.html`/`.puml`/`.feature`/`.json`/`.jsonl`），由 M9 Orchestrator 编排读写（`architecture.md` §3.4）。
2. **门禁串行，开发并行**：④⑤⑥ 三道质量门串行（责任链清晰）；②③ 内部前后端并行（`sprint-plan.md` §6 并行度说明）。

## 2. Sprint 内流水线逐步定义

### 步骤 ①：架构师审核规约（P1）

| 项 | 内容 |
|---|---|
| **触发** | Sprint 开工：PM P8 下发本 Sprint 工作包（范围=该 Sprint 卡片的 F-xx/模块/端点清单） |
| **输入** | Sprint 工作包；架构基线：`architecture.md`、`class-diagram.puml`、`sequence-diagrams/*.puml`、`data-model.md`、`api-spec.md`；GWT 契约（该 Sprint 验收判据引用的 feature 文件） |
| **输出** | **开工许可**（已审核规约说明：本 Sprint 涉及模块的类/端点/文件契约清单 + 结构合规 checklist）；接口变更记录（如有） |
| **失败分支** | 发现工作包与架构基线矛盾（如端点 Schema 冲突、模块边界越界）→ 开**规约问题单**：小改由 P1 按基线裁决并记录；涉架构基线本身变更 → 走 §4.3 变更说明流程（出变更说明→用户确认→更新基线），**不得静默偏离基线**（H8 前提） |

### 步骤 ②：前端 + 后端并行开发（P2 ∥ P3）

| 项 | 内容 |
|---|---|
| **触发** | P1 开工许可签发 |
| **输入（前端 P2）** | 原型 HTML（`02_UX_DESIGN/wireframes/*.prototype.html`，直接作为 **UI 实现模板**，§7.2/C4）；`api-spec.md` 端点 Request/Response Schema；P1 checklist |
| **输入（后端 P3）** | P1 已审核规约；`class-diagram.puml`（实现类结构必须一致）；该 Sprint 端点清单（E-xx） |
| **输出（前端 P2）** | Renderer 页面组件 + **Mock 契约实现**（按 Schema 造假数据，**不阻塞后端**，§11.5 协作流程 2）；页面可见性自查记录 |
| **输出（后端 P3）** | 引擎模块实现 + E-xx 端点实现 + 文件读写协议实现（临时文件+原子重命名/JSONL 追加，`architecture.md` §3.4） |
| **并行规则** | 两线零等待并行：前端对着 Mock 开发完整交互，后端对着规约开发引擎；中间产物互不阻塞 |
| **失败分支** | 任一线生成/构建失败 → **进入 §4 异常自愈流程**（≤3 次自修复→熔断→回滚）；发现规约缺口 → 提规约问题单回 ①（P1 裁决期间并行线不整体停摆，仅阻塞受影响模块） |

### 步骤 ③：前后端联调（P2 + P3）

| 项 | 内容 |
|---|---|
| **触发** | 前端 Mock 页面完成 **且** 后端对应端点完成（§11.5 协作流程 3：后端接口完成后前后端联调） |
| **输入** | 前端组件（Mock 版）+ 后端真实端点；联调清单（该 Sprint E-xx 逐端点） |
| **输出** | 联调通过的可运行增量（Mock 切换真实端点，页面行为与原型一致）；联调记录 |
| **失败分支** | 联调缺陷 → 按 E-xx 定位责任侧（Schema 不符/实现偏差）→ 回 ② 局部修复后重新联调；**同缺陷累计进入自愈计数**（§4：单问题 ≤3 次自修复）；Schema 本身有误 → 回 ① 走变更流程 |

### 步骤 ④：代码审查（P6）

| 项 | 内容 |
|---|---|
| **触发** | 步骤 ③ 联调通过 |
| **输入** | 本 Sprint 代码增量（P2+P3 diff）；P1 结构合规 checklist；安全合规要点（沙箱白名单/IPC 暴露面/预览服务本机回环/文件原子写/NFR-01 本地红线/埋点无侵入） |
| **输出** | 审查结论二值：**approve** / **change requests**（逐条意见清单，可追溯） |
| **失败分支** | change requests → 退回 P2/P3 修复（逐条闭环）→ 重新走 ③（如涉接口行为）与 ④ 重审；审查不通过**不得**进入步骤 ⑤；结构类问题（类结构 ≠ PlantUML）不归 P6 —— 退回 ① 由 P1 处理（H8 归属） |

### 步骤 ⑤：测试Agent 执行 GWT（P5）

| 项 | 内容 |
|---|---|
| **触发** | 步骤 ④ approve |
| **输入** | 联调增量；GWT 契约：该 Sprint 验收判据引用的 `06_TESTS/features/*.feature` 场景（含正常/边界/异常三类） |
| **输出** | 结构化测试报告（`test-reports/{reportId}.json`：通过率、逐场景结果、失败步骤，按 F-xx 聚合）；L3 文案契约检查记录 |
| **执行纪律** | 场景全部通过 → 报告交步骤 ⑥；**任一场景未通过 → 退回 ②/③ 修复，修复后先重跑失败场景，再全量重跑**（`test-plan.md` §6.3 回归优先，防修复引入新回归）；重跑链路带时间戳留档可追溯 |
| **失败分支** | 失败场景涉及生成/构建层面失败 → 同时计入 §4 自愈流程；用户侧**不暴露任何失败细节**，只见人话进度（F-19） |

### 步骤 ⑥：裁判校验与合并（M5 JudgeEngine → 合并）

| 项 | 内容 |
|---|---|
| **触发** | 步骤 ⑤ 测试报告通过率 100%（该 Sprint 验收范围 + 全量回归口径） |
| **输入** | 测试报告（H7：PRD 功能全覆盖核对）；M4 `extractStructure()` 代码结构提取结果 vs `class-diagram.puml`（**H8：代码结构 ≡ PlantUML**）；该 Sprint 涉及的文档产物（NFR-05 双标准抽查）；时序图调用序列比对（`sequence-diagrams/*.puml`） |
| **输出** | 判定结论（`05_PROJECT_PLAN` 相关判定经 E-23/E-24 可查）：**通过 → 合并** / **退回** |
| **通过后动作** | 合并增量 → PM P8 登记 Sprint 收口 → M2 `appendChangelog()` 自动追加 `07_VERSIONS/changelog.md` 版本条目（F-22-03）→ 若为里程碑 Sprint 触发发布流程（`sprint-plan.md` §4）→ 用户以生活化确认页确认交付（E-10，长期型用户确认点） |
| **失败分支** | 退回 → 退回单列明缺项（场景缺失/结构不符/文档缺项）→ 回 ②/③ 修复 → 重走 ⑤⑥；**长期迭代型不限退回次数，必须通过后方可进入下一阶段**（F-16-05、需求源 §9.3）；每次退回-修复-重跑链路留档（支撑审计）；退回不改变 Sprint 边界（新增需求走 backlog，`sprint-plan.md` §1.2） |

> 流水线与模板推荐配置（§11.5）逐条对齐：架构师产出 API Spec 后前后端同步开工（①→②）→ 前端 Mock 不阻塞（②）→ 后端完成后联调（③）→ Reviewer 审查（④）→ 测试Agent执行 GWT（⑤）→ 裁判校验 → 合并（⑥）；Sprint 节奏每段 ≤2 周、每段交付可运行增量（`sprint-plan.md` §1.2）。

## 4. 异常自愈流程（需求源 §6.3，两种模式通用）

### 4.1 流程图

```
编程Agent执行任务（步骤②③⑤ 中任一环）
   │
   ├─ 成功 → 继续（流水线下一步）
   │
   └─ 失败 → 自动修复（最多 3 次，每次可选不同策略；
   │          策略由编程Agent团队自主决策，向导Agent不介入，R1）
   │
   ├─ 修复成功 → 继续
   │
   └─ 3 次仍失败 → 熔断触发
         │
         ▼
      回滚到上一个健康快照（M8 SnapshotManager；只做线性回滚，
      当前版本先存为快照再恢复，内容不丢失，ADR-04）
         │
         ▼
      向导Agent播报安抚文案（F-19 契约，逐字使用）：
      "刚才的修改没有成功，已回到上一个正常版本，你的内容没有丢失。"
         │
         ├─ 快消型：换个技术方案重新尝试（编程层闭环，全程不倒回向导Agent改需求）
         └─ 长期迭代型（本项目模式）：
              如涉及设计约束不可实现 → 出具生活化变更说明
              → 用户确认 → 调整实现方案（不倒回需求阶段，不重开需求对话）
```

### 4.2 责任矩阵（对齐 `00_AGENT_ROLES.md` §6）

| 阶段 | 动作 | 责任方 |
|---|---|---|
| 触发 | 生成/构建/测试失败信号 | M7（测试失败）/ 构建过程（P2/P3 执行侧）→ 喂给 M9·c RepairLoop |
| 自修复 | ≤3 次，策略可换（回退重放/改写实现/换依赖路径等），团队自主决策 | M9·c RepairLoop + 编程Agent团队（R1） |
| 熔断 | 3 次修复仍失败即熔断 | M9·c |
| 回滚 | 回滚到上一健康快照（快照自动管理：初版生成/确认修改前后/模式转换/**异常回滚前**四时机，F-08） | M8（回滚执行者） |
| 用户告知 | 熔断回滚话术（§4.1 逐字文案；五类安抚文案见 §7.5 契约） | 向导Agent M1（唯一对话出口，F-19） |
| 长期型后续 | 变更说明 → 用户确认 → 调整方案 | 编程Agent（出具）+ 用户（确认） |
| 记录 | 自修复触发/结果埋点（尝试次数 + 最终结果，§12.4 #10） | M6 TelemetryCollector |
| **不参与** | **裁判Agent不参与自愈**（门禁只卡阶段交接）；**需求分析师 G1 不被重新激活**（R2/R3/R5） | — |

### 4.3 边界规则（六条硬规则，逐条引用需求源 §6.3）

| # | 规则 |
|---|---|
| R1 | 自愈由编程Agent团队自主决策修复策略，向导Agent不介入修复过程 |
| R2 | 编程层闭环：异常在编程层内解决，不倒回向导Agent改需求 |
| R3 | 不倒回需求阶段：长期型也只调整实现方案（出变更说明→用户确认），不重开需求对话 |
| R4 | 熔断回滚后必须告知用户且内容不丢失（快照管理 + 安抚文案） |
| R5 | 裁判Agent不参与自愈；自修复触发/结果作为埋点事件记录（尝试次数 + 最终结果） |
| R6 | 长期型变更说明 = 唯一允许突破设计约束的通道，且须用户确认 |

### 4.4 自愈与流水线的耦合点

| 流水线步骤 | 自愈入口 | 熔断后动作 |
|---|---|---|
| ② 并行开发 | 生成/构建失败 | 回滚该改动所在快照 → 长期型按 §4.1 后续路径（换实现方案重试或变更说明） |
| ③ 联调 | 同一联调缺陷累计修复 ≤3 次 | 回滚联调改动 → 回 ② 换实现策略 |
| ⑤ GWT | 场景运行失败退回后的修复尝试 | 回滚修复改动（测试基线不受污染）→ 修复策略重选 |
| ⑥ 裁判退回 | 退回修复属流程内修复，**不计入自愈 3 次上限**（裁判退回次数独立计数，长期型不限） | — |

## 6. 跨 Sprint 交接与上下文不丢失约定

| # | 约定 | 依据 |
