## 1. 计划总则

### 1.1 输入与拆分依据

| 依据 | 内容 |
|---|---|
| 需求源 §14 四阶段路线 | Phase 1 核心主轴（MVP）→ Phase 2 长期迭代型 → Phase 3 体系完善 → Phase 4 数据与科研，展开为 Sprint 序列 S0…S15（共 16 个 Sprint） |
| PRD §5 优先级 | P0×12（F-01/F-02/F-03/F-05/F-06/F-08/F-09/F-10/F-13/F-15/F-16/F-19）先交付；P1×9 与 P2×3 按阶段排入（PRD §4 优先级图例：P0=Phase 1，P1=Phase 2–3，P2=Phase 4） |
| GWT 契约前置 | `06_TESTS/features/*.feature` 89 场景为**编码前验收契约**（用户裁决 #4）：每个 Sprint 的验收判据直接引用既有 feature 文件与场景编号，编码期不新立验收标准 |
| 架构模块边界 | 每个 Sprint 的工作包按 `architecture.md` §4 模块划分（M0–M9）与 §6 F-xx→模块映射切分，代码结构须符合 `class-diagram.puml`（裁判硬约束 H8） |
| 端点对照 | 每个 Sprint 涉及的端点引用 `api-spec.md` E-01…E-30 编号（§5 端点↔F-xx↔模块对照表） |

### 1.2 节奏基线

| 项 | 约定 |
|---|---|
| Sprint 时长 | **每个 Sprint = 2 周**（10 个工作日），全程无更粗粒度；总日程 = 16 个 Sprint = 32 周（W01–W32） |
| 日历基线 | W01 = 用户确认本计划与开发节奏后的第一个工作周（对用户以生活化周数呈现，符合 §7.6 零基础交互原则，不暴露排期技术细节） |
| 交付判定 | 每个 Sprint 收口 = 该 Sprint 范围内 GWT 场景**全量重跑 89 条通过率 100%**（`test-plan.md` §6.3：先重跑失败场景再全量回归）+ 裁判校验通过（F-15/F-16），方可合并为可运行增量 |
| 用户确认点 | ① 本 Sprint 计划与节奏（F-22-01，S0 开工前）；② 里程碑版本交付确认（v0.1.0/v0.2.0/v0.3.0/v1.0.0 各一次，走 E-10 确认文档流程）；长期型每题带「你帮我决定」选项（F-11-02） |
| 变更规则 | Sprint 范围一经确认不中途加塞：新增需求进 backlog，由工程经理在下一个 Sprint 开工前重新裁决；**超过两周的拆分被退回重新拆分**（F-22-02 边界保障同样约束本计划自身的修订） |

### 1.3 版本号约定（详见 §5）

每个 Sprint 收口的可运行增量即一次版本发布，写入 `07_VERSIONS/changelog.md`（F-22-03）；四个里程碑版本：**v0.1.0（MVP）、v0.2.0（长期迭代型完整流程）、v0.3.0（体系完善）、v1.0.0（数据与科研）**。

## 5. 版本发布节奏与 changelog 约定

| 项 | 约定 |
|---|---|
| 发布单元 | **每个 Sprint 收口 = 一次版本发布**（可运行增量过裁判校验并合并后才计版本；未通过裁判校验的增量不写入版本发布，F-22-04） |
| 版本号 | 里程碑版本 `v0.1.0 / v0.2.0 / v0.3.0 / v1.0.0`；里程碑间 Sprint 递增 patch（v0.0.1…v0.3.2，见 §2 总览表收口版本列） |
| changelog 维护 | 每次版本发布由 M2 DocGenEngine `appendChangelog()` **自动**追加 `07_VERSIONS/changelog.md` 条目（版本号/日期/新增功能/修复/已知问题），历史版本可查（F-22-03）——不人工手写，杜绝遗漏 |
| 回滚联动 | 版本发布基于 M8 快照链；发布后发现问题按 F-08 线性回滚，回滚动作同步记入 changelog 备注（不产生新版本号） |
| 对用户呈现 | 版本信息仅以生活化语言在交付确认时呈现（"你的应用更新到了新版本，这次新增了……"），不暴露版本号技术细节之外的概念（§7.6） |
