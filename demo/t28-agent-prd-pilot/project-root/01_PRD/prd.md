## 1. 项目概述

### 1.1 项目名称

**向导Agent与编程Agent多智能体协同开发平台**

### 1.2 一句话定位

一款**桌面应用**：让完全不会编程的普通人，只靠自然语言对话，就能把想法变成能运行、可迭代的软件。

### 1.3 核心价值主张

> "告诉它你想做什么，它帮你做好。"

- **对用户**：不需要学编程、不需要懂架构、不需要配置开发环境。用户只需描述想法，系统完成从需求→设计→编码→测试→交付的全闭环（需求源 §1.2）。
- **对研究者**：全量采集用户交互数据，量化分析非专业人员使用自然语言驱动 AI 开发的最佳范式（需求源 §1.2）。

### 1.4 产品形态

- 桌面应用（Windows / macOS / Linux），基于 Proma 源码 fork（需求源 §1.3）。
- 编程 Agent 在用户**本地**运行；SaaS 版本为远期规划，不在本版本范围。
- 向导 Agent 团队与编程 Agent 团队之间以完整文件体系交接，不引入重量级中间件（需求源 §13.1）。

## 2. 目标用户

### 2.1 用户分层（引需求源 §2）

| 层级 | 用户 | 特征 | 典型代表 |
|------|------|------|---------|
| **P0 主要目标用户** | 完全零基础的非专业用户 | 不具备任何编程知识，不懂 HTML/CSS/JS，不了解数据库、前后端概念；有明确想法但不知如何技术实现；希望做出实际可用的工具；不能/不愿投入时间学编程 | 文科生、商学院学生、普通办公人员（访谈画像 A/B/C，见 `dialogue-simulated.md`） |
| **P1 次要用户** | 有基础概念但不写代码的人 | 知道网页、数据库等基本概念，能理解技术术语，但自己不写代码 | 懂一点技术的产品、运营 |
| **研究用户（内部）** | 课题组成员/研究者 | 通过后台数据看板分析用户行为数据，提炼"自然语言最佳交互指令范式" | 课题组研究者 |

### 2.2 核心恐惧点与产品应对（引需求源 §2.4，经访谈第 2/3 轮印证）

| 恐惧点 | 产品应对 | 对应条目 |
|--------|---------|---------|
| 怕看到代码 | 默认不展示源码，预览优先 | F-05、NFR-05 |
| 怕搞坏东西 | 操作前自动快照，随时可回滚 | F-08 |
| 怕隐私泄露 | 数据脱敏说明，本地运行保障 | NFR-01 |
| 怕 AI 做的东西不对 | 原型预览确认 + 测试报告收口 | F-05、F-15 |
| 怕操作太复杂 | 卡片选择代替文本输入，单选代替填空 | F-02 |
| 怕等待焦虑 | 超过 5 秒显示进度提示文案 | F-19、NFR-04 |

### 2.3 零基础交互原则（引需求源 §7.1/§7.6）

- 用户始终只看到一个聊天界面，没有技术配置面板；
- 向导 Agent 不说技术术语，用生活化语言描述；
- 原型预览是最主要的确认方式；
- 偏好卡片选择而非长文本输入，偏好单选而非填空；
- 每个选择问题提供「你帮我决定」选项（访谈 I-11）。

## 3. 两种产品模式（差异已作为功能条目写入 §5）

用户启动应用后面对**两道门**，必须明确选择其一，不可模糊进入（F-01）。快消型可在进行中或完成后升级为长期迭代型（F-12）。

### 3.1 模式差异总表

| 维度 | 快消型（Quick MVP） | 长期迭代型（Long-term Iteration） | 对应功能条目 |
|------|--------------------|---------------------------------|-------------|
| 适用场景 | 一次性工具、小应用、验证想法 | 持续更新版本的项目（开源工具、商业产品、长期个人项目） | F-01 |
| 核心理念 | 快速实现，测试收口 | 完整软件工程方法论驱动 | F-10 / F-11 |
| 文档完备度 | 精简文档（PRD+原型+GWT 测试），砍掉工程管理文档 | 全文档完备后才开工编码 | F-03 / F-04、F-10 / F-11 |
| 主约束 | BDD+GWT 为核心验收机制，PlantUML 可省略或极简 | PlantUML 类图+时序图为主约束，BDD+GWT 为行为验证补充 | F-15、F-16 |
| 架构设计师/工程经理 | 隐于后台，全自动决策，不对用户暴露 | 跳到前台，与用户确认设计方案和 Sprint 规划 | F-10 / F-11 |
| 交付标准 | 测试用例全量通过 = 交付合格 | 每个 Sprint 交付可运行增量并通过裁判校验 | F-15、F-22 |
| 用户确认点 | 功能清单 + 原型（2 处） | 功能清单、原型、设计方案、Sprint 节奏（4 处）（访谈 I-15） | F-10 / F-11 |
| 异常处理 | 编程层闭环换方案重试，不倒回需求 | 出具变更说明→用户确认→调整方案，不倒回需求阶段 | F-18 |
| 裁判严格度 | 核心硬约束；软约束仅查 PRD-GWT 对应；退回 2 次上限后提示人工介入 | 全量硬约束+全部软约束维度；不限退回次数，必须通过（需求源 §9.3） | F-16 / F-17 |
| 模式升级 | 可升级为长期迭代型（已完成软件作为起点文档） | — | F-12 |

### 3.2 模式转换规则（需求源 §3.3）

- 快消型项目进行中或完成后均可升级为长期迭代型；
- 系统建议先完成快消型全过程以充分激发想法（用户可坚持立即升级）；
- 升级时以已完成的软件作为起点文档，补全正式文档体系后进入规范化迭代流程。

### 5.2 功能需求详情（验收标准为 GWT 要点句，供 W4 生成 GWT feature 对账）

#### F-01 启动两道门模式选择（P0）

- **描述**：用户启动应用新建项目时，界面只呈现「快消型」「长期迭代型」两张模式卡片，必须点选其一才能进入；选择入口同时告知"快消型以后可以升级为长期项目"以降低选择焦虑（访谈 I-13）。
- **优先级依据**：需求源 §14 Phase 1——快消型完整流程为 MVP 主轴。
- **验收标准（GWT 要点）**：
  - Given 用户首次启动并新建项目，When 尚未选择模式，Then 系统不进入任何工作区，仅展示两张模式卡片。
  - Given 用户在两道门界面，When 点击「快消型」卡片，Then 系统创建快消型项目并直接进入需求对话，全程零技术配置。
  - Given 两道门界面展示中，When 用户查看任一模式说明，Then 能看到"快消型之后可以升级为长期项目"的提示。
  - Given 用户关闭后重新打开未完成项目，When 项目恢复，Then 保持原模式继续，不重复强制选择。

#### F-02 需求对话与多轮需求挖掘（P0）

- **描述**：向导 Agent 以多轮对话挖掘需求，每轮 3–5 个问题；问题以选项卡片呈现、单选为主，每个问题附「你帮我决定」选项；用户可用自然语言补充自己关心的验收场景（"我想确认一下如果……"）（需求源 §6.1、§7.6、§8.3）。
- **优先级依据**：需求源 §14 Phase 1——需求对话是快消流程第一步。
- **验收标准（GWT 要点）**：
  - Given 用户用一句生活化语言描述想法，When 一轮对话开始，Then 向导提出 3–5 个问题且每个问题提供可点选卡片与「你帮我决定」选项。
  - Given 每轮对话结束，When 系统记录需求要点，Then 用户可随时查看一份生活化的"已确认需求清单"。
  - Given 用户补充自定义验收关切，When PRD 定稿，Then 该关切被转写为对应功能的验收场景并纳入测试范围。
  - Given 用户表达含糊（如"电脑为主手机也能看"），When 系统无法唯一理解，Then 以生活化复述请用户确认而非追问技术细节。

#### F-03 精简PRD产出（快消型）（P0）

- **描述**：快消型在需求对话收敛后产出精简 PRD：含项目名称、目标用户、核心功能列表、验收标准四要素（满足需求源 §9.2 硬约束），文档零基础可读，随后立即进入原型与编码（需求源 §5.3、§6.1）。
- **优先级依据**：需求源 §14 Phase 1。
- **验收标准（GWT 要点）**：
  - Given 快消型需求对话收敛（用户确认或全部选「你帮我决定」），When 系统生成精简 PRD，Then 文档包含项目名称、目标用户、核心功能列表、验收标准四要素。
  - Given 精简 PRD 已生成，When 零基础用户阅读，Then 开头即可看懂"给谁用、做什么"，正文无未解释的技术术语。
  - Given 精简 PRD 呈现给用户，When 用户确认，Then 系统进入原型生成阶段并开始快消管线。

#### F-04 完整PRD与用户故事产出（长期迭代型）（P1）

- **描述**：长期迭代型产出全量 PRD（目标用户、F-xx 功能列表、每项 GWT 验收标准）与符合 INVEST 原则的用户故事文档；用户签字确认后方可进入下一阶段（需求源 §5.2、§6.2）。
- **优先级依据**：需求源 §14 Phase 2——长期迭代型完整流程。
- **验收标准（GWT 要点）**：
  - Given 长期型需求对话收敛，When 用户签字确认，Then 系统产出完整 PRD 与用户故事文档。
  - Given 完整 PRD 产出，When 裁判校验，Then 每个 F-xx 均有验收标准且编号唯一无冲突。
  - Given 用户故事文档产出，When 检查映射，Then 每条 US-xx 恰好对应一个 F-xx。

#### F-05 可交互HTML原型生成（P0）

- **描述**：向导 Agent（UI/UX 顾问角色）生成带内联 CSS/JS 的**单文件 HTML 原型**：双击即可在浏览器打开，可点击、可跳转、含模拟数据；应用内预览默认不展示任何源码；前端开发 Agent 直接以原型 HTML 作为 UI 实现模板（需求源 §7.2、§2.4）。
- **优先级依据**：需求源 §14 Phase 1。
- **验收标准（GWT 要点）**：
  - Given 精简/完整 PRD 经用户确认，When 系统生成原型，Then 产出单文件 HTML，双击即可在浏览器打开并可点击跳转。
  - Given 原型在应用内预览，When 用户查看，Then 界面不出现任何源代码，只展示可交互页面。
  - Given 原型包含模拟数据，When 用户按访谈高频操作走一遍，Then 主要路径（如增、改状态、查看汇总）均可演示。

#### F-06 原型视觉模型辅助审查（P0）

- **描述**：系统截图 HTML 原型交带视觉能力的多模态模型审查布局与可用性问题；用户也可直接截图圈注问题发回，系统将圈注转为修改意图（需求源 §7.2）。
- **优先级依据**：需求源 §14 Phase 1——UI/UX 顾问带视觉模型并行工作为基础角色配置。
- **验收标准（GWT 要点）**：
  - Given 原型 HTML 已生成，When 系统截图并送视觉模型审查，Then 产出问题清单并自动修正明显问题后再次进入预览。
  - Given 用户发回一张圈注截图，When 系统接收，Then 向导将圈注位置转为修改意图并进入修改流程，且以生活化语言复述理解。

#### F-07 点选纠错（P1）

- **描述**：用户在预览区点击或框选不满意的界面元素，系统捕获元素位置与上下文，向导 Agent 将其转为修改规约，编程 Agent 执行修改，预览区自动刷新（需求源 §7.3）。
- **优先级依据**：需求源 §14 Phase 3——点选纠错完整实现。
- **验收标准（GWT 要点）**：
  - Given 用户在预览区，When 点击或框选某元素并说明期望，Then 系统捕获该元素位置与上下文并生成修改规约。
  - Given 修改规约已生成，When 编程 Agent 完成修改，Then 预览区自动刷新且目标元素按期望更新。
  - Given 本次点选纠错为较大改动，When 执行修改前，Then 系统已自动保存快照，可一键回滚（联动 F-08）。

#### F-08 时间轴自动快照与线性回滚（P0）

- **描述**：系统在关键节点自动保存版本快照（初版生成、用户确认修改前后、模式转换、异常回滚前）；快照附时间戳与自然语言描述；用户可一键回到任意旧版本，回滚不丢失当前版本；**只做线性回滚，不做版本分支**；用户不可手动建快照（需求源 §7.4）。
- **优先级依据**：需求源 §14 Phase 1——线性回滚快照。
- **验收标准（GWT 要点）**：
  - Given 初版生成/确认修改前后/模式转换/异常回滚前任一关键节点到达，When 节点触发，Then 系统自动保存快照并附时间戳与一句自然语言描述。
  - Given 用户查看历史版本列表，When 选择任一旧版本并确认回滚，Then 当前版本先存为快照，再恢复所选旧版本。
  - Given 用户已回滚并继续修改，When 查看时间轴，Then 旧版本之后的快照保留为存档，界面不出现"分支"概念。
  - Given 任意界面，When 用户寻找"手动创建快照"入口，Then 不存在该入口（快照仅由系统自动管理）。

#### F-09 向导Agent角色切换与静默路由（P0）

- **描述**：用户始终只面对一个"向导 Agent"；需求分析师、UI/UX 顾问、架构设计师、工程经理作为独立角色（System Prompt+模型配置）在后台按对话阶段静默切换，UI 自然过渡，上下文不丢失；用户不感知背后角色数量（需求源 §4.2、§4.3）。
- **优先级依据**：需求源 §14 Phase 1——基础角色（需求分析师+UI/UX 顾问并行+架构设计师隐于后台）；架构/工程经理前台交互随 F-11（P1）交付。
- **验收标准（GWT 要点）**：
  - Given 项目处于任意阶段，When 用户发送消息，Then 对话界面始终只呈现单一"向导"，无角色选择器与技术配置面板。
  - Given 对话从需求阶段进入原型阶段，When 系统内部切换角色，Then 用户不感知切换，且前文上下文在后续对话中不丢失。
  - Given 需求阶段，When 需求分析师与 UI/UX 顾问并行工作，Then 对话产出与原型产出保持一致的需求口径（同一份已确认需求清单）。

#### F-10 快消型自动化执行管线（P0）

- **描述**：快消型"快速实现，测试收口"：PRD+原型确认后，架构设计师与工程经理隐于后台自动完成技术选型、接口推断、团队分配；编程 Agent 编码；测试 Agent 跑全量 GWT；裁判判定通过后交付试用+反馈改进循环（需求源 §3.1、§6.1）。
- **优先级依据**：需求源 §14 Phase 1——快消型完整流程跑通。
- **验收标准（GWT 要点）**：
  - Given 快消型 PRD 与原型已确认，When 用户点击「开始做」，Then 系统自动完成选型/组队/编码/测试，用户仅看到人话进度提示，不被询问技术问题。
  - Given 快消型编码完成且 GWT 全量通过，When 裁判判定，Then 交付可运行版本并进入试用反馈循环。
  - Given 快消型过程中发生架构/工程决策，When 决策产生，Then 决策记录在后台文档，不向用户弹出技术确认。

#### F-11 长期迭代型规范化执行管线（P1）

- **描述**：长期型"全文档完备后才开工"：完整 PRD+用户故事经裁判第一道关后，架构设计师跳到前台产出架构方案（用户以生活化卡片确认），工程经理跳到前台产出团队配置与 Sprint 计划（用户确认节奏），随后按 Sprint 交付可运行增量（需求源 §3.2、§6.2）。
- **优先级依据**：需求源 §14 Phase 2。
- **验收标准（GWT 要点）**：
  - Given 长期型项目文档体系未完备，When 用户请求开工，Then 系统不开工编码，由裁判退回并列出缺失文档清单。
  - Given 架构方案与 Sprint 计划产出，When 需要用户确认，Then 系统以生活化卡片请用户确认，且每个问题带「你帮我决定」选项。
  - Given 某 Sprint 交付，When 裁判校验通过，Then 交付可运行增量并写入版本变更记录（联动 F-22）。

#### F-12 模式转换（快消→长期升级）（P1）

- **描述**：快消型进行中或完成后可升级为长期型；系统建议先完成快消全过程；升级以已完成软件为起点文档，补全正式文档体系后进入长期管线；转换前后各存一份快照（需求源 §3.3、§7.4）。
- **优先级依据**：需求源 §14 Phase 2（长期迭代型完整流程配套）。
- **验收标准（GWT 要点）**：
  - Given 快消型项目进行中或已完成，When 用户选择「升级为长期项目」，Then 系统先提示"建议先完成快消全过程"，用户可坚持立即升级。
  - Given 用户确认升级，When 转换完成，Then 已交付软件成为长期项目起点文档，缺失的正式文档被列出并补全。
  - Given 模式转换执行，When 转换前后，Then 系统各保存一份自动快照（联动 F-08）。

#### F-13 编程Agent团队激活与协作（P0）

- **描述**：向导 Agent/工程经理根据项目特征从角色池激活编程 Agent（架构师、前端、后端、全栈、测试工程师、代码审查员、DevOps、项目经理）；激活哪些角色由工程模板+动态判断决定；团队配置对用户完全透明（需求源 §4.4）。
- **优先级依据**：需求源 §14 Phase 1——快消最小团队（全栈开发+测试工程师）；角色池全激活随 Phase 3（F-14/F-11 配套）。
- **验收标准（GWT 要点）**：
  - Given 快消型项目进入编码阶段，When 系统组建团队，Then 激活最小团队（全栈开发+测试工程师）且用户界面不出现任何角色配置信息。
  - Given 长期迭代型大型项目，When 工程经理按模板判断需要，Then 按角色池激活多角色且职责边界在后台文档中明确（用户不可见）。
  - Given 团队内任一角色完成工作，When 交接给下一角色，Then 通过项目文件体系交接，交接物完整可追溯。

#### F-14 工程模板体系与自动推断（P1）

- **描述**：六类模板（Web全栈、移动App、桌面工具、CLI/脚本、硬件联调、AI应用）预定义团队配置、文档清单、协作流程、Sprint 节奏；向导 Agent 从对话关键词自动推断匹配，对用户不可见，仅以生活化复述请用户确认；支持第三方插件注册与 JSON/YAML 导入（需求源 §11）。
- **优先级依据**：需求源 §14 Phase 3——模板体系全部实现+自动推断（Phase 1 以内置默认模板支撑快消流程）。
- **验收标准（GWT 要点）**：
  - Given 用户对话中出现项目类型表述（如"做个网站/处理数据/连设备"），When 系统推断，Then 自动匹配六类模板之一且推断过程对用户不可见。
  - Given 推断完成，When 系统向用户确认，Then 仅以生活化表述确认（如"你想做的是一个网页小站"），用户可纠正并重新匹配。
  - Given 第三方模板插件或 JSON/YAML 配置文件，When 注册/导入，Then 模板库收录并参与后续推断。

#### F-15 GWT测试场景生成与测试收口（P0）

- **描述**：PRD 定稿后，系统为每个功能项自动生成 GWT（Given-When-Then）场景，覆盖正常路径+边界条件+异常输入；测试 Agent 运行全量场景输出通过率报告；**全部通过 = 交付合格**（需求源 §8.3、§10）。Phase 1 以功能项→GWT 场景生成+全量通过收口；Phase 2 起落盘为 `06_TESTS/features/*.feature` 文件并由 GWT 测试执行器运行。
- **优先级依据**：需求源 §14 Phase 1（快消收口机制）/Phase 2（Feature 文件自动生成与执行）。
- **验收标准（GWT 要点）**：
  - Given PRD 定稿含功能列表，When 系统生成测试，Then 每个功能项至少对应一个 GWT 场景且覆盖正常、边界、异常三类。
  - Given GWT 测试全量运行完成，When 全部场景通过，Then 系统输出通过率报告并向用户播报生活化结论（访谈 I-10）。
  - Given 任一场景未通过，When 裁判判定，Then 交付被退回编程 Agent 修复，不向用户交付（联动 F-16）。
  - Given（P1 增强）长期型项目，When 测试落盘，Then `06_TESTS/features/` 下每个功能项有对应 `.feature` 文件。

#### F-16 裁判Agent硬约束门禁（P0）

- **描述**：裁判 Agent 是两团队之间的独立流程门禁（流程门禁，不是质量审计员）：文档/代码不经裁判通过不能进入下一阶段。硬约束为不可通融的结构化检查（PRD 四要素、GWT 对应存在性等，全表见需求源 §9.2）；快消型核心项检查、退回 2 次上限后提示人工介入；长期型全量硬约束、不限次必须通过（需求源 §9、§9.3）。
- **优先级依据**：需求源 §14 Phase 1——硬约束基础版（PRD+GWT 存在性）；全量硬约束随 Phase 2。
- **验收标准（GWT 要点）**：
  - Given 文档提交进入下一阶段前，When 裁判执行硬约束检查，Then PRD 缺项目名称/目标用户/核心功能列表/验收标准任一项即被退回并说明缺项。
  - Given 快消型交付判定，When 裁判检查，Then 逐项核对每个 PRD 功能项都有对应 GWT 场景，缺失即退回。
  - Given 快消型同一文档被退回 2 次后再次不通过，When 判定完成，Then 系统提示需要人工介入。
  - Given 长期迭代型文档退回，When 判定，Then 不设退回次数上限，必须通过后方可进入下一阶段。

#### F-17 裁判Agent软约束评估（P1）

- **描述**：裁判 Agent 以 AI 方式评估质量维度：逻辑一致性、可测试性、完整性、可读性（零基础用户能否大致理解），给出通过/建议改进/退回三档结论（需求源 §9.2）。
- **优先级依据**：需求源 §14 Phase 2——软约束 AI 评估。
- **验收标准（GWT 要点）**：
  - Given 文档已通过硬约束，When 裁判软约束评估，Then 输出四维度各自结论与理由（通过/建议改进/退回）。
  - Given 文档含未经生活化解释的技术术语，When 可读性评估，Then 标记"建议改进"并指出术语位置。

#### F-18 异常自愈与熔断回滚（P1）

- **描述**：编程 Agent 执行失败时自动修复，最多 3 次、可采用不同策略；3 次仍失败触发熔断：回滚到上一健康快照并告知"修改没有成功，已回到上一个正常版本，你的内容没有丢失"；快消型在编程层换技术方案闭环（不倒回需求）；长期型如涉及设计约束不可实现则出具变更说明→用户确认→调整方案（不倒回需求阶段）（需求源 §6.3）。
- **优先级依据**：需求源 §14 Phase 3——异常自愈+熔断回滚（Phase 1 快消流程内置简化重试：同一方式最多重试一次；完整"3 次不同策略+熔断"随本项交付）。
- **验收标准（GWT 要点）**：
  - Given 编程 Agent 执行失败，When 自动修复启动，Then 最多尝试 3 次且可采用不同策略，期间用户仅看到"还在处理"类人话进度。
  - Given 3 次修复均失败，When 熔断触发，Then 系统回滚到上一健康快照并播报 F-19 指定的失败安抚文案。
  - Given 快消型熔断后，When 重新尝试，Then 在编程层更换技术方案闭环，不倒回需求对话。
  - Given 长期迭代型熔断且设计约束不可实现，When 处置，Then 出具生活化变更说明并等待用户确认后调整方案，不倒回需求阶段。

#### F-19 心理防御文案与进度安抚（P0）

- **描述**：超过 5 秒的操作显示进度提示；等待/修改成功/修改失败/回滚完成/操作超时五类场景按需求源 §7.5 文案表播报安抚话术；任何报错不以技术堆栈形式呈现给用户（需求源 §7.5、§2.4）。
- **优先级依据**：需求源 §14 Phase 1 用户体验底线（访谈 I-08/I-14 强需求）。
- **验收标准（GWT 要点）**：
  - Given 任一操作持续超过 5 秒，When 等待中，Then 界面显示进度提示文案（含"只发生在安全环境，不影响你的电脑文件"）。
  - Given 修改失败/回滚完成/操作超时事件发生，When 文案播报，Then 使用需求源 §7.5 对应文案，不出现技术报错内容。

#### F-20 全量埋点采集（P2）

- **描述**：全量、无侵入式静默埋点，覆盖六层数据：用户交互、向导 Agent、编程 Agent、裁判 Agent、Token 经济、项目元数据；关键埋点事件 13 项（项目创建、每轮对话、角色切换、PRD 确认、原型确认、撤销、点选纠错、模式转换、编程执行、自修复触发、裁判判定、满意度、完成/放弃）（需求源 §12.1–§12.4）。
- **优先级依据**：需求源 §14 Phase 4。
- **验收标准（GWT 要点）**：
  - Given 用户任意交互事件发生，When 事件落库，Then 按需求源 §12.4 事件清单逐项记录且界面无任何打扰。
  - Given 科研分析数据写出，When 脱敏处理，Then 数据不含真实业务 payload（如用户私人笔记内容）。

#### F-21 后台分析看板与实验支持（P2）

- **描述**：面向研究者的后台看板：效率看板（MVP 触达时间、成功闭环率）、Token 效率图、认知摩擦指数（意图修正次数/总交互轮数）、文档合规趋势、范式挖掘；支持 A/B 对照实验（对照组=原生大模型聊天，实验组=本平台）的分组与指标导出（需求源 §12.6、§12.7）。
- **优先级依据**：需求源 §14 Phase 4。
- **验收标准（GWT 要点）**：
  - Given 研究者打开后台看板，When 查看任一分析视图，Then 数据可按项目类型筛选并导出。
  - Given A/B 实验配置完成，When 实验运行，Then 支持对照组与实验组核心指标（控制权让渡偏好、认知摩擦、Time-to-MVP、首次构建成功率、自修复成功率）对比导出。

#### F-22 Sprint规划与版本管理（P1）

- **描述**：长期迭代型由工程经理产出 Sprint 分解（每个 Sprint ≤2 周且为可交付增量）与团队配置；版本发布自动更新 changelog（需求源 §5.2、§6.2、§9.2）。
- **优先级依据**：需求源 §14 Phase 2（Sprint/版本随长期流程）/Phase 3（版本管理与跨会话交接完善）。
- **验收标准（GWT 要点）**：
  - Given 长期型项目开工前，When 工程经理产出 Sprint 计划，Then 每个 Sprint 拆分至 ≤2 周的可交付增量并经用户确认节奏。
  - Given 某版本发布完成，When 更新变更记录，Then changelog 自动追加该版本条目且历史版本可查。

#### F-23 跨版本与跨会话上下文交接（P1）

- **描述**：不同 Agent 在版本间平滑交接、上下文不丢失；跨会话继续项目时无需用户复述历史（需求源 §3.2、§14 Phase 3）。
- **优先级依据**：需求源 §14 Phase 3。
- **验收标准（GWT 要点）**：
  - Given 新会话或新角色接管进行中的项目，When 接管完成，Then 已确认的需求清单、设计约束与进度完整可用，用户未被要求复述历史。
  - Given 版本间角色交接，When 接管发生，Then 既有确认结论不被默默更改；如需变更须走变更说明流程（联动 F-18）。

#### F-24 Figma设计稿导入（远期可选）（P2）

- **描述**：通过 Figma REST API 导出设计稿作为原型素材的**备选**路径，面向有 Figma 账号的用户；不作为主路径，不影响主流程（需求源 §7.2）。
- **优先级依据**：需求源标注"远期可选增强"；归入 Phase 4 后的可选项。
- **验收标准（GWT 要点）**：
  - Given 用户已配置 Figma 账号，When 选择从 Figma 导入，Then 系统导出设计稿并转为原型素材。
  - Given 用户未配置 Figma，When 使用平台，Then 主流程（对话→原型）完全不受影响。
