## 第 1 轮：你想用平台做什么（意图挖掘）

**受访画像**：A 林小满
**分析师目标**：确认用户带着什么想法来、高频使用场景、期望载体。

### 1.1 分析师问题

1. 你想用这个平台做一个什么样的东西？它是给谁用的？
2. 你现在是怎么处理这件事的？哪个环节最麻烦？
3. 如果这个东西做出来了，你一天大概会打开它几次？最常做的三件事是什么？
4. 你希望它「住」在哪里——手机上、电脑上，还是打开网页就能用？

### 1.2 模拟用户回答

> **林小满**：
> 1. 我想给我们部门做一个「内容排期小工具」。我们组 6 个人，都在不同平台发内容（公众号、小红书、视频号），谁哪天要发什么、发没发，现在全靠一张共享表格，经常撞车。它是给全组人用的，主要是我们主管想一眼看到「这周发了什么、漏了什么」。
> 2. 现在用共享表格，最麻烦的是：改了日期没人知道；谁负责哪条要看备注猜；到点没人提醒，全靠我在群里喊。
> 3. 估计一天打开三四次吧。最常做的三件事：①往里加一条新内容排期；②把发完的标成「已发」；③周一开会前把本周的表投屏给大家看。
> 4. 电脑上用吧，开会投屏方便。不过最好手机上也能看一眼，有时候在外面跑活动。

### 1.3 分析师记录（对 PRD 功能的影响）

| # | 记录 | 影响条目 |
|---|------|---------|
| 1 | 用户能清楚说出「给谁用、解决什么麻烦」，但完全无法说出技术形态——需求对话应顺着「谁用/多常用/高频三件事」引导，而不是问技术选型 | F-02；prd.md §2、§5 |
| 2 | 「共享表格的三个麻烦」= 真实需求清单的雏形：状态标记、负责人、到期提醒——精简 PRD 的功能列表应从这类痛点反推 | F-03；需求源 §6.1 |
| 3 | 高频操作是「增、改状态、周视图展示」三类——原型必须把这三天路径做成可点击演示 | F-05；需求源 §7.2 |
| 4 | 「电脑为主、手机能看」属于典型模糊表述——应由系统推断为 Web 项目模板并向用户生活化确认（"你想要一个网页小站，电脑手机都能打开"） | F-14；需求源 §11.3 |

## 第 2 轮：你怕什么（§2.4 恐惧点）

**受访画像**：B 陈昊
**分析师目标**：逐项核对需求源 §2.4 恐惧点是否为真实用户感受，挖掘未列出的恐惧。

### 2.1 分析师问题

1. 如果有一个「AI 听你说话就帮你做软件」的工具，你第一个担心会是什么？
2. 如果 AI 做出来的界面你不喜欢，你会怎么办？
3. 你怕不怕它把你之前已经做好的东西改坏了？
4. 你会不会担心你在里面说的话、写的内容被别人看到或者传到网上？
5. 如果它卡住转圈很久没反应，你心里会想什么？你希望它怎么做？

### 2.2 模拟用户回答

> **陈昊**：
> 1. 最怕它甩给我一堆代码，说"你自己改一下吧"。我看不懂代码，一看到黑乎乎的英文符号就想关掉。
> 2. 不喜欢就让它改呗。但最好是能直接在那个页面上指出来——"这里不好看"、"这个按钮挪走"，比打字描述容易多了。
> 3. 怕！特别怕。比如我已经调好的一个页面，让它加个新东西，结果整个都乱了。那我不是白干了？所以最好改之前能存个档，坏了能退回去。
> 4. 有点担心。我写的东西可能有个人信息的。至少得告诉我它存在哪儿、谁能看到。要是全存在我自己电脑上，我就放心多了。
> 5. 转圈超过一会儿我就慌了，会想"是不是死机了？我是不是把它点坏了？"。希望它起码跟我说一声"我在干活，别急"，或者告诉我"刚才没成功，但你的东西没丢"。

### 2.3 分析师记录（对 PRD 功能的影响）

| # | 记录 | 影响条目 |
|---|------|---------|
| 1 | 「怕看到代码」被印证为最强恐惧——界面默认不展示源码，一切确认走预览 | F-05；NFR-05；需求源 §2.4、§7.6 |
| 2 | 「指着界面说哪里不好」= 点选纠错是零基础用户的自然表达方式，优先级依据充分 | F-07；需求源 §7.3 |
| 3 | 「改坏东西、能退回去」= 自动快照+线性回滚是安全感的核心来源，且用户主动提出"改之前存档" | F-08；需求源 §7.4 |
| 4 | 「数据在哪儿、谁能看到」= 隐私必须用生活化语言主动告知（"都在你自己电脑上"），不能只写在隐私条款里 | NFR-01；F-19；需求源 §2.4、§12.2 |
| 5 | 「转圈恐慌」= 等待超过 5 秒必须有进度提示，失败必须有"你的东西没丢"安抚，与 §7.5 文案逐条对应 | F-19；NFR-04；需求源 §7.5 |

## 第 3 轮：怎么确认「做对了」（验收观）

**受访画像**：C 周老师
**分析师目标**：弄清零基础用户用什么标准判断成品合格，能否接受文档/测试作为验收语言。

### 3.1 分析师问题

1. 东西做完之后，你怎么判断"这就是我想要的"？
2. 你能看懂技术文档或者代码吗？你愿意看吗？
3. 如果它生成一份很长的方案文档让你"确认"，你会怎么办？
4. 什么情况下你会觉得"这东西不行，我不要了"？

### 3.2 模拟用户回答

> **周老师**：
> 1. 打开页面，长得像我想的那个样子，然后我自己把常用的操作从头到尾点一遍：收笔记、看谁交了、导出名单。都顺，就是做对了。
> 2. 看不懂，也不愿意看。我教语文的，代码对我来说就是天书。
> 3. 说实话我只看开头。"这是给谁用的、有哪些功能"我能看懂；后面密密麻麻的就跳过了，然后点"你帮我决定"。
> 4. 改了好几次都改不到点子上，或者它悄悄把我做好的东西改没了，又说不清改了哪儿。这种我就不要了。反过来，如果它每一步都跟我说清楚"我做了什么、测试都过了"，我还是愿意再试的。

### 3.3 分析师记录（对 PRD 功能的影响）

| # | 记录 | 影响条目 |
|---|------|---------|
| 1 | 「原型点一遍」= 原型预览是用户最主要的确认方式，"你觉得这个页面看起来对吗"优于"请确认第几节" | F-05；需求源 §7.2、§7.6 |
| 2 | 「测试都过了」可以被翻译成人话成为信任来源——测试报告收口要向用户播报生活化结论（"你要的几种用法都试过了，都通过"） | F-15；需求源 §10 |
| 3 | 长文档只看开头 → PRD 自身要"零基础可读"（开头即项目名/用户/功能/验收四要素），且任何确认问题都带「你帮我决定」选项 | F-02、F-03、F-04；NFR-05；需求源 §7.6、§9.2 |
| 4 | 「说不清改了哪儿」会被抛弃 → 失败/回滚必须明确告知+可回退，裁判退回要有次数上限与人工介入提示，避免无限折腾 | F-18、F-16、F-19；需求源 §6.3、§9.3 |

## 第 4 轮：两道门、中途变卦与意外（模式与异常体验）

**受访画像**：A 林小满（回访）
**分析师目标**：验证两道门模式选择的可理解性、快消→长期升级的真实动机、异常场景的期望处置。

### 4.1 分析师问题

1. 一开始就让你选：「快速做个一次性的小工具」还是「做一个要长期更新、越做越正式的项目」，你会选哪个？为什么？
2. 假如你先做了个一次性的排期表，用着用着发现整个部门离不开它了，想把它变成正式项目慢慢加功能，你希望怎么办？
3. 如果 AI 把东西改坏了，而且它自己修不好，你希望它怎么跟你说？
4. 中途要等很久的时候，你希望屏幕上出现什么？
5. 整个过程里，你愿意参与多少确认？是每一步都问你，还是关键几步问你、其余它自己拿主意？

### 4.2 模拟用户回答

> **林小满**：
> 1. 先选快的。我们下周就要用，先有个能跑的再说。不过如果开头就告诉我"以后可以升级成正式项目"，我更安心，不会觉得选错。
> 2. 那最好能"转正"——把这个能用的当作底子，补上正式的计划，接着加功能，而不是从头再来。
> 3. 先老实说"这次没改成功"，然后告诉我"已经退回上一个正常版本，你的东西一点没丢"，最后给我两个选择："换个办法再试"或者"先这样，明天再说"。千万别让我看报错。
> 4. 一句人话进度，比如"正在帮你搭页面，大概还要一两分钟，都在安全环境里，不影响你电脑"。再给我个能看的小进度条。
> 5. 关键的两三次问我就行：定功能、看页面效果、最终交付前。其余的让它自己决定，问多了我烦。

### 4.3 分析师记录（对 PRD 功能的影响）

| # | 记录 | 影响条目 |
|---|------|---------|
| 1 | 「先快后正式」是典型路径 → 两道门必须在入口就告知"快消型之后可以升级"，降低选择焦虑；选择必须二选一不可模糊 | F-01、F-10；需求源 §3 |
| 2 | 「拿能用的当底子转正」= 模式转换以已交付软件为起点文档，补全文档后进入长期管线，不推倒重来 | F-12；需求源 §3.3 |
| 3 | 异常话术三段式（认错→保底→给选择）直接对应熔断回滚后的用户告知文案 | F-18、F-19；需求源 §6.3、§7.5 |
| 4 | 「人话进度+安全保证」验证 ≤5 秒提示与安抚文案的必要性 | F-19；NFR-04 |
| 5 | 「关键两三次确认」→ 快消型确认点=功能清单+原型；长期型增加架构方案与 Sprint 节奏两次前台确认，其余全部后台自动决策 | F-10、F-11；需求源 §3.1、§3.2、§6.2 |
