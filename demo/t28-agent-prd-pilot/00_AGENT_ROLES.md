## 1. Agent 架构总览与用户视角

### 1.1 三大 Agent 体系 + 一个独立裁判模块（§4.1）

| 体系 | 包含角色 | 体系定位 | 对用户可见性 |
|---|---|---|---|
| 向导Agent团队 | 需求分析师、UI/UX顾问、架构设计师、工程经理（4 角色） | 需求与文档侧：与用户对话，产出开编程前文档体系 | 用户始终只面对"一个向导Agent"对话；角色在后台静默切换 |
| 编程Agent团队 | 架构师、前端开发、后端开发、全栈开发、测试工程师（测试Agent）、代码审查员、DevOps工程师、项目经理（8 角色池） | 实现侧：编码、测试、审查、部署、进度管理 | 完全透明，用户不感知团队配置 |
| 裁判Agent（独立模块） | 单角色，独立于两团队 | 流程门禁：文档/代码不经裁判通过，不能进入下一阶段 | 用户不可见（判定结果以自然语言反馈体现） |
| （两团队关系） | 文档体系交接（§4.1 图 / §5.1） | 向导Agent团队 ⇄ 编程Agent团队以完整文件体系（目录结构）作为交付物和沟通基础 | — |

### 1.2 用户视角（§4.2）

| 条目 | 内容 |
|---|---|
| 对话入口 | 用户始终只面对一个"向导Agent"进行对话 |
| 角色切换 | 后台静默切换，UI 自然过渡；对话路由层按当前阶段加载对应角色的 System Prompt（§13.3） |
| 用户须知 | 用户不需要知道、也不应该感知背后有多少个 Agent 角色在工作 |

### 1.3 角色实现机制（§4.3 / §13.2 / §13.3）

| 条目 | 内容 |
|---|---|
| 角色定义 | 每个角色 = 独立 System Prompt 文件 + 模型 API 配置 |
| 加载方式 | 系统根据对话阶段自动路由加载（对话路由层） |
| 模型调度 | 多模型 API 并发调用；视觉多模态模型用于 UI 原型审查与点选纠错；长上下文 SOTA 用于架构设计与全局把控 |

## 2. 向导Agent团队：4 角色（§4.3）

### 2.1 角色总表（§4.3 表逐行保留）

| # | 角色 | 职责 | 模型策略 | 激活时机 |
|---|---|---|---|---|
| G1 | 需求分析师 | 与用户对话、挖掘需求、引导思考、撰写PRD | 对话能力强、有耐心、善于引导 | 项目启动、需求变更时 |
| G2 | UI/UX顾问 | 设计页面布局、交互流程、产出可交互HTML原型 | 带视觉能力的国产多模态模型 | 与需求分析师**并行**，涉及前端UI需求时 |
| G3 | 架构设计师 | 技术选型、PlantUML建模、API规范设计 | 逻辑推理强、长上下文SOTA模型 | PRD确认后（快消型隐于后台，长期迭代型跳到前台） |
| G4 | 工程经理 | 确定编程Agent团队配置、协作流程、Sprint规划 | 长上下文SOTA、理解软工方法论 | 架构设计后（快消型隐于后台，长期迭代型跳到前台） |

### 2.2 逐角色职责细目

#### 2.2.1 需求分析师（G1）

| 维度 | 内容 | 出处 |
|---|---|---|
| 核心职责 | 与用户对话、挖掘需求、引导思考、撰写PRD | §4.3 |
| 对话节奏 | 多轮深度对话，每轮最少 3–5 个问题（动态上限），逐步诱发用户真实意图；渐进式，不一次性抛出大量问题 | §6.1 / §6.2 / §7.1 |
| 产出物 | 快消型：精简PRD（含UX原型描述）；长期迭代型：完整PRD + 用户故事（符合 INVEST 原则），经用户确认/签字 | §5.2 / §5.3 / §6.1 / §6.2 |
| 交互语言 | 不说技术术语，用生活化语言描述；偏好卡片选择而非长文本输入；提供"你帮我决定"选项 | §7.6 |
| 后续衔接 | PRD 定稿后触发 GWT 场景自动生成（§8.3）；PRD 为裁判 Agent 第一道关的检查对象（§9.2） | — |
| 再次激活 | 需求变更时重新激活（§4.3）；但编程层异常自愈**不倒回**需求阶段（§3.1 / §6.3） | — |

#### 2.2.2 UI/UX顾问（G2）

| 维度 | 内容 | 出处 |
|---|---|---|
| 核心职责 | 设计页面布局、交互流程、产出可交互HTML原型 | §4.3 |
| 原型产出 | 带内联 CSS/JS 的单文件 HTML 原型，含模拟数据，可点击、可跳转；用户双击即可浏览器预览 | §7.2 |
| 视觉审查 | 调用带视觉能力的国产多模态模型，截图 HTML 原型审查 UI 布局与可用性问题；用户可截图标注问题回传 | §4.3 / §7.2 |
| 产出物 | 快消型：核心页面原型；长期迭代型：全页面 HTML 原型 + 设计系统（design-system.md）+ 交互规范（interaction-spec.md）、sitemap、user-flows | §5.2 / §5.3 / §6.2 |
| 下游影响 | 原型 HTML 是前端开发 Agent 的 **UI 实现模板**（直接作为模板使用） | §7.2 |
| 点选纠错衔接 | 用户点选原型元素 → 向导Agent将点击位置与上下文转换为修改规约 → 编程Agent执行修改 | §7.3 |

#### 2.2.3 架构设计师（G3）

| 维度 | 内容 | 出处 |
|---|---|---|
| 核心职责 | 技术选型、PlantUML 建模、API 规范设计 | §4.3 |
| 快消型产出（隐于后台） | 自动技术选型、自动推断 API、简版架构方案（不暴露给用户） | §6.1 |
| 长期迭代型产出（跳到前台） | PlantUML 类图 + 时序图 + 数据模型；技术选型方案 → 用户确认 | §6.2 |
| 产出落点 | `03_ARCHITECTURE/`（architecture.md、class-diagram.puml、sequence-diagrams/*.puml、data-model.md）、`04_API_SPEC/api-spec.md` | §5.2 |
| PlantUML 约束 | 产出 `.puml` 机读文件而非图片；Phase 1 约束类图（类/属性/方法/关系）与时序图（API 调用序列） | §8.4 |
| 对用户透明 | PlantUML 对非专业用户完全透明；长期迭代型设计确认时用户只看到结构化功能描述，不接触 PlantUML 代码 | §8.4 |

#### 2.2.4 工程经理（G4）

| 维度 | 内容 | 出处 |
|---|---|---|
| 核心职责 | 确定编程Agent团队配置、协作流程、Sprint 规划 | §4.3 |
| 快消型（隐于后台） | 自动分配编程 Agent（如全栈开发 + 测试Agent），不对用户暴露 | §6.1 |
| 长期迭代型（跳到前台） | 编程Agent团队配置 + Sprint 分解 + 协作流程；与用户确认开发节奏 | §6.2 |
| 产出落点 | `05_PROJECT_PLAN/`：team-config.md（团队角色配置）、sprint-plan.md（Sprint 分解与里程碑）、workflow.md（协作流程定义） | §5.2 / §6.2 |
| 团队配置决定权 | 激活哪些编程 Agent 角色、采用什么协作流程，由**工程模板 + 向导Agent 动态判断**（工程经理承担决定） | §4.4 / §11.1 |

### 2.3 快消型 vs 长期迭代型：模式差异（§3.1 / §3.2 / §4.3 / §6.1 / §6.2）

| 角色 | 快消型（Quick MVP） | 长期迭代型（Long-term Iteration） |
|---|---|---|
| 需求分析师 | 多轮对话（每轮≥3–5 问）→ 精简PRD + 用户确认 | 多轮深度沟通 → 完整PRD + 用户故事（INVEST）→ 用户签字确认 |
| UI/UX顾问 | 同步产出核心页面 HTML 原型辅助沟通 | 全页面 HTML 原型 + 设计系统 + 交互规范 |
| 架构设计师 | **隐于后台**：全自动技术选型/API 推断，方案不暴露给用户 | **跳到前台**：与用户确认技术选型与 PlantUML 设计方案 |
| 工程经理 | **隐于后台**：自动分配编程 Agent，自动化决策，不对用户暴露 | **跳到前台**：与用户确认团队配置、Sprint 规划与开发节奏 |
| 模式差异总则 | 全自动决策，不对用户暴露（§4.3 关键协作关系） | 需用户确认设计方案和工程计划（§4.3 关键协作关系） |

### 2.4 关键协作关系与交接边界（§4.3 / §5.1 / §6.1 / §6.2 / §7.2）

| # | 关系 | 内容 | 出处 |
|---|---|---|---|
| C1 | 需求分析师 ∥ UI/UX顾问 **并行** | 图形化界面的描述也是揭示需求的过程；两者共同完成完整 PRD（含 UX 原型） | §4.3 / §6.1 / §6.2 |
| C2 | 架构设计师 / 工程经理 模式差异 | 快消型全自动决策不对用户暴露；长期迭代型需用户确认设计方案和工程计划 | §4.3 |
| C3 | 向导团队 → 编程团队交接边界 | 以完整文件体系（目录结构）为交付物与沟通基础；文档必须机器可解析（裁判可自动校验）+ 人可阅读（零基础用户能大致看懂） | §5.1 |
| C4 | UI/UX顾问 → 前端开发 | 原型 HTML 直接作为 UI 实现模板 | §7.2 |
| C5 | 架构设计师 → 编程Agent架构师 | PlantUML 规约 = 代码结构强约束；架构师负责审核代码结构符合 PlantUML | §4.4 / §8.4 |
| C6 | 需求分析师 隔离边界 | 编程层异常自愈全程不倒回向导Agent改需求（快消）/不倒回需求阶段（长期），需求分析师不介入实现期异常 | §3.1 / §6.1 / §6.3 |
| C7 | 团队 → 裁判 | 每阶段产出（PRD/架构/API/计划/代码/测试报告）须过裁判门禁方可进入下一阶段 | §9.1 |

## 3. 编程Agent团队：8 角色池（§4.4）

### 3.1 角色池总表（§4.4 表逐行保留）

| # | 角色 | 职责 | 激活条件 |
|---|---|---|---|
| P1 | 架构师 | 审核设计规约、保证代码结构符合PlantUML约束 | 长期迭代型必选 |
| P2 | 前端开发 | 实现UI界面、对接API、交互逻辑 | 有UI需求时激活 |
| P3 | 后端开发 | 实现API、数据库、业务逻辑 | 有后端需求时激活 |
| P4 | 全栈开发 | 前后端一体实现（小型项目） | 快消型或小型项目 |
| P5 | 测试工程师（测试Agent） | 编写运行GWT测试用例、回归测试、输出测试报告 | 所有项目必选 |
| P6 | 代码审查员 | 代码质量检查、安全审查、合规校验 | 长期迭代型必选 |
| P7 | DevOps工程师 | CI/CD配置、部署脚本、环境管理 | 需要部署时激活 |
| P8 | 项目经理 | 追踪Sprint进度、协调阻塞、风险预警 | 大型多Sprint项目 |

### 3.2 激活与配置机制（§4.4 / §11）

| 条目 | 内容 | 出处 |
|---|---|---|
| 激活主体 | 向导Agent根据项目特征从角色池中激活所需编程 Agent 角色 | §4.4 |
| 判断依据 | 激活哪些角色、采用什么协作流程，由**工程模板 + 向导Agent动态判断**（工程经理执行配置） | §4.4 / §11.1 |
| 模板推断 | 模板由向导Agent根据用户对话关键词自动匹配（Web全栈/移动App/桌面工具/CLI脚本/硬件联调/AI应用 六类），对用户不可见 | §11.1 / §11.3 |
| 透明性承诺 | **团队配置由向导Agent/工程经理决定，对用户完全透明**（用户不感知） | §4.4 |
| 模板预定义内容 | 推荐团队角色配置、标准文档清单、协作流程、Sprint 节奏 | §11.1 / §11.5 |

### 3.3 模板推荐配置示例（§11.2 / §11.5）

| 模板 | 典型项目 | 团队配置（激活的角色） |
|---|---|---|
| Web全栈 | 博客、商城、管理后台 | 架构师 + 前端 + 后端 + 测试（长期迭代型另加代码审查员） |
| 移动App | Flutter/React Native | UI + 逻辑 + 后端 + 测试 |
| 桌面工具 | PyQt/Tauri 效率工具 | 全栈 + 测试 |
| CLI/脚本 | 数据处理、自动化 | 全栈Agent（单Agent） |
| 硬件联调 | IoT、嵌入式 | 固件 + 上位机 + 硬件测试 |
| AI应用 | 调用 LLM API 的应用 | 后端 + Prompt工程 + 测试 |

### 3.4 编程团队内部协作流水线（长期迭代型 Sprint，§6.2）

| 序 | 步骤 | 责任角色 |
|---|---|---|
| 1 | 审核设计规约 | 架构师（P1） |
| 2 | 前端 + 后端并行开发（前端以原型 HTML 为模板、Mock 数据先行） | 前端（P2）/ 后端（P3）/ 全栈（P4，小项目） |
| 3 | 代码质量/安全/合规审查 | 代码审查员（P6） |
| 4 | 执行 GWT 测试、回归、输出测试报告 | 测试工程师/测试Agent（P5） |
| 5 | 校验代码结构 ≡ PlantUML、PRD 功能全覆盖 → 通过/退回 | 裁判Agent（独立模块） |
| 6 | 通过则合并；Sprint 交付与进度追踪 | 项目经理（P8，大型项目）；DevOps（P7）负责 CI/CD 与部署 |

## 4. 裁判Agent：独立流程门禁（§9）

### 4.1 定位（§9.1 / §4.5）

| 条目 | 内容 |
|---|---|
| 组织位置 | 两个 Agent 团队之间的**独立流程门禁**（独立模块，不隶属任何一队） |
| 门禁规则 | 文档/代码**不经裁判通过，不能进入下一阶段** |
| 本质定位 | **裁判Agent 是流程门禁，不是质量审计员**——只检查"交接是否到位"，不深入审计具体代码质量（代码质量是编程Agent内部各角色/Reviewer 的职责） |
| 检查对象 | 测试是否全部通过；代码结构是否匹配 PlantUML；PRD 功能是否全部有测试对应；文档体系硬约束满足性 |

### 4.2 硬约束清单（§9.2 表逐条保留，不可通融，不通过直接退回）

| # | 检查对象 | 硬约束示例 |
|---|---|---|
| H1 | PRD | 必须包含：项目名称、目标用户、核心功能列表、验收标准 |
| H2 | 架构设计 | 必须包含：技术选型及理由、模块划分、模块依赖关系 |
| H3 | PlantUML | 类图/时序图语法有效，类关系完整 |
| H4 | API Spec | 每个端点必须定义：Method、Path、Request/Response Schema |
| H5 | Sprint Plan | 必须拆分到 ≤2周粒度的可交付增量 |
| H6 | Team Config | 必须列出激活的角色、职责边界、交付物 |
| H7 | GWT测试 | 每个PRD功能项必须有对应的GWT场景 |
| H8 | 代码结构 | 代码结构与PlantUML类图的一致性 |

### 4.3 软约束维度（§9.2，AI 评估，给出通过/建议改进/退回）

| # | 评估维度 | 评估内容 |
|---|---|---|
| S1 | 逻辑一致性 | PRD的功能与架构的模块是否对齐？ |
| S2 | 可测试性 | PRD中每个功能是否都有对应的GWT测试场景？ |
| S3 | 完整性 | 异常情况、边界条件是否被覆盖？ |
| S4 | 可读性 | 零基础用户能否大致理解文档内容？ |

### 4.4 两种模式的裁判严格度差异（§9.3）

| 维度 | 快消型 | 长期迭代型 |
|---|---|---|
| 硬约束检查 | 核心项（PRD + GWT测试存在性） | 全量硬约束（H1–H8） |
| 软约束评估 | 仅 PRD-GWT 对应关系 | 全部维度（S1–S4） |
| 退回次数上限 | **2 次**（超过则人工介入提示） | **不限**，必须通过 |

### 4.5 裁判在各流程关卡的位置（§6.1 / §6.2 / §8.2 / §10.3）

| 关卡 | 检查内容 | 出处 |
|---|---|---|
| 第一道关（长期迭代型，PRD 签字确认后） | 文档体系硬约束 + 软约束审查 → 退回/通过 | §6.2 |
| 编码后校验 | 测试报告全量通过？代码结构 ≡ PlantUML？PRD 功能全覆盖？ | §6.1 / §6.2 / §4.5 |
| 交付判定 | 运行全量 GWT，输出通过率报告；全部通过 = 交付合格 | §10.3 |
| 结构校验方式 | 读取代码 → 提取实际类结构/API 调用序列 → 与 PlantUML 规约逐项对比 → 输出合规报告 | §8.4 |

### 4.6 可复用为调度Agent（§9.4）

| 条目 | 内容 |
|---|---|
| 复用形态 | 裁判Agent 可兼职**调度Agent** |
| 调度范围 | 编程Agent团队内部：根据不同阶段的工作包，调度对应的编程Agent角色按流程协作 |
| 与门禁关系 | 调度与门禁共用同一"裁判引擎"模块（硬约束规则执行 + 软约束 AI 评估 + 调度控制，§13.3） |

## 5. 测试Agent vs 裁判Agent：职责边界（§4.5）

| 维度 | 测试Agent（编程Agent团队·测试工程师 P5） | 裁判Agent（独立模块） |
|---|---|---|
| 比喻 | **执行者（运动员）** | **判定者（裁判员 / 流程门禁）** |
| 核心问题 | "代码能不能跑通验收场景？" | "交接是否到位？" |
| 动作 | 执行 GWT 测试用例；回归测试；输出测试报告 | 综合判定；输出通过/退回 |
| 关注点 | 测试覆盖率、通过率 | 测试是否全部通过；代码结构是否匹配 PlantUML；PRD 功能是否全部有测试对应 |
| 明确不管 | — | **不管代码质量和具体实现细节**（不深入审计代码质量——那是编程Agent内部各角色的职责） |
| 输入/输出衔接 | 输入：代码 + GWT 场景；输出：测试报告 → 交裁判 | 输入：测试报告 + 代码结构 + PlantUML + PRD；输出：通过/退回 |
| 责任归属 | 跑测试、给数据 | 做判定、卡门禁 |

> 一句话边界（§4.5 原文）：裁判Agent 是流程门禁，不是质量审计员。它只检查"交接是否到位"，不深入审计具体代码质量——那是编程Agent内部各角色的职责。

## 6. 异常自愈机制中的角色分工（§6.3）

### 6.1 自愈流程与责任矩阵

| 阶段 | 动作 | 责任角色 | 出处 |
|---|---|---|---|
| 触发 | 生成/构建/测试失败 | 编程Agent（执行层） | §6.3 |
| 自动修复 | 自动修复，最多 **3 次**；每次可选不同修复策略；具体策略由**编程Agent团队自主决策** | 编程Agent团队（自主决策权） | §6.3 |
| 熔断 | 3 次修复仍失败 → 熔断触发 | 编程Agent团队 | §6.3 |
| 回滚 | 回滚到上一个健康快照（快照由系统自动管理：初版生成、确认修改前后、模式转换、异常回滚前均自动快照；只做线性回滚） | 快照管理器（系统机制，§13.3）/ 编程Agent触发 | §6.3 / §7.4 |
| 用户告知 | 回滚后以安抚文案告知用户（熔断回滚话术责任）："刚才的修改没有成功，已回到上一个正常版本，你的内容没有丢失。"（向导Agent是面向用户的唯一对话出口，§4.2） | 向导Agent（对话出口，使用 §7.5 心理防御文案） | §6.3 / §7.5 |
| 后续路径·快消型 | **换个技术方案重新尝试（编程层闭环）**——全程不倒回向导Agent改需求 | 编程Agent团队 | §6.3 / §3.1 |
| 后续路径·长期迭代型 | 如涉及**设计约束不可实现** → 出具变更说明 → 用户确认 → 调整实现方案（**不倒回需求阶段**） | 编程Agent（出具变更说明）；用户（确认） | §6.3 / §3.2 |

### 6.2 自愈机制的边界规则（角色分工的核心约束）

| # | 规则 | 出处 |
|---|---|---|
| R1 | 自愈由编程Agent团队自主决策修复策略，向导Agent不介入修复过程 | §6.3 |
| R2 | **编程层闭环**：异常在编程层内解决，快消型全程不倒回向导Agent改需求（需求分析师 G1 不被重新激活） | §6.3 / §3.1 |
| R3 | **不倒回需求阶段**：长期迭代型也只调整实现方案（出变更说明→用户确认），不重开需求对话 | §6.3 / §3.2 |
| R4 | 熔断回滚后必须告知用户且内容不丢失（快照管理 + 安抚文案） | §6.3 / §7.4 / §7.5 |
| R5 | 裁判Agent不参与自愈（门禁只卡阶段交接）；自修复触发/结果作为埋点事件记录（尝试次数 + 最终结果） | §12.4 #10 |
| R6 | 长期迭代型变更说明 = 唯一允许突破设计约束的通道，且须用户确认 | §6.3 |
