组合式编排：到底几层？谁管谁？

看文字容易觉得“多画了一层”——大概率是因为把 引擎 当成了 会话。这张图先把这两个东西分开：引擎是插件/服务，不是会话，不占会话深度。

组合层数怎么数
按引擎嵌套次数：tree→flow = 2 层
会话深度怎么变
每嵌一层引擎，只在当前会话下面 +1 层
“管理者”是谁
就是调用内层引擎的那个会话本身，不是新会话

① 只有 tree —— 单层引擎

一个树引擎管一张任务树；“任务节点层级”是树自己的层级，体现为逐层派发出来的会话。

组合层数：1引擎：tree
d0根会话（root leaf 的 owner）tree 账本起点
d1└─指挥官 leaf 会话commandertree_dispatch 起子会话
d2└─执行 leaf 会话worker干活 + tree_report 回报
tree 引擎（插件/服务，不是会话，不占层）维护任务树账本：依赖/DoD/派发/收割/竹节
📌
一句话：树的“两层”是任务节点的层级，会话按派发逐层 +1；引擎本身不占一层会话。

② 只有 flow —— 单层引擎

一个流程引擎跑一张 DAG；所有流程节点会话都挂在“调用 flow 的那个会话”下面，是同级平铺，不是一层套一层。

组合层数：1引擎：flow
d0根会话（调用 flow_run 的会话）flow 引擎的父会话
d1├─流程节点 N1 会话一次性会话
d1├─流程节点 N2 会话一次性会话
d1└─流程节点 N3 会话一次性会话
flow 引擎（插件/服务，不是会话，不占层）决定顺序/传值/journal/门禁
📌
注意：N1/N2/N3 是同一个深度的兄弟会话；flow 的“顺序”是引擎的调度逻辑，不是会话嵌套。

★ 两层 A：tree 的叶子会话带一张 flow

叶子/commander 会话自己就是内层 flow 的父会话（管理者/锚点），flow 节点会话直接挂在它下面 +1 层。中间没有“flow 管理者会话”。

组合层数：2（tree + flow）✅ S1 真机已验证最大会话深度：2
d0根会话tree 账本
d1└─tree 叶子会话 ★= flow 的父会话 / 管理者它自己调 flow_run 并等结果
d2├─flow 节点 N1 会话
d2├─flow 节点 N2 会话
d2└─flow 节点 N3 会话
tree 引擎（管 d0–d1 的任务树）不占层
flow 引擎（管 d2 的 DAG + journal）不占层
🎯
这就是“叶子直接驱动 +1 层流程会话”：d1 的叶子既是 tree 的 leaf，也是 d2 那三个节点的父会话；没有额外一层。差别只在“谁做调度”——flow 引擎调度 d2，叶子只负责发包和收结果。

③ 两层 B：flow 的一个节点会话带一棵 tree

反向同样成立：flow 的节点会话直接当 tree 的指挥官（真管理者），tree worker 挂在它下面 +1 层；也没有额外一层。

组合层数：2（flow + tree）⏳ 机制成立，待真机验证最大会话深度：2
d0根会话（调 flow_run）flow 引擎
d1└─flow 节点会话 ★= tree commander / 真管理者它调 tree_plan / tree_dispatch / harvest / verify
d2├─tree worker A 会话
d2└─tree worker B 会话
flow 引擎（管 d0–d1 的流程）不占层
tree 引擎（管 d1–d2 的子树）不占层
📌
不对称点：d1 的节点会话是真的“调度员”（自己派、自己收、自己验）；而 A 图里的叶子只是“发包人”（内层顺序由 flow 引擎定）。两者都不额外占一层。

④ 三层：tree → flow → tree

三层 = 引擎嵌套三次。每嵌套一次仍然只 +1 层会话；问题不是“多画层”，而是 maxDepth=4 会被用满。

组合层数：3（tree + flow + tree）⚠ 深度零余量maxDepth=4
d0根会话
d1└─tree commander leaf 会话
d2└─tree worker 会话 ★它调 flow_run（flow 的父会话）
d3├─flow 节点会话
d3└─flow 节点会话（= 内层 tree commander）★
d4├─内层 tree worker A 会话第 4 层 = 满
d4└─内层 tree worker B 会话第 4 层 = 满
d5✕verify / judge / handoff / 再嵌一层 → 第 5 层SubagentDepthError
⚠️
为什么三层危险：不是“多了一层画”，而是会话深度正好用满。任何再起子会话的动作（验证评审、交接、再嵌）都会撞 maxDepth=4。
换个挂载点可能放得下：若 flow 挂在更浅的 d1 上（而不是 d2 的 worker），内层 worker 会在 d3、verify 在 d4 —— 刚好。所以“三层能不能跑”取决于挂在哪一级叶子，不是抽象的“三层”。

⑤ 对照：感觉“多画了一层”，多的是哪一层？

多出来的是一个并不存在的“管理者会话”。实际结构里，管理者 = 调用内层引擎的那个会话本身（下图 d1 的叶子），它直接当 d2 节点的父会话。

❌ 错误理解：多画了一层“flow 管理者会话”

d0根会话
d1└─tree 叶子会话
d2└─“flow 管理者会话” ← 不存在
d3├─flow 节点会话
d3└─flow 节点会话

多一层会话、总深度变成 3，且这个“管理者”没有任何真实身份。

✅ 实际结构：叶子自己就是父会话

d0根会话
d1└─tree 叶子会话 ★ 管理者
d2├─flow 节点会话
d2└─flow 节点会话

只有 3 个深度层级（d0–d2），引擎在幕后记账，不占层。

💡
一句话纠正：“管理者”不是第三种会话，而是一个会话的两种身份——d1 的叶子在 tree 里是 leaf，在 flow 里是父会话/管理者。所以两层组合只加 +1 层，不是 +2 层。
证据：S1 组合真机 E2E（tree leaf 内跑 3 节点 flow，flow 节点 depth=2，relay off 下 315 秒成功）· v0.8.0 relay 开关 E2E（off 生效、auto 复现取消）· 组合评估文档 §4.3 深度算术（内层 worker 第 4 层 = 满）。
