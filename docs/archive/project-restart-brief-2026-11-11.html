先回答你的四个问题

每条结论都附现场证据；点开「证据」可直接看到我读的是哪个文件 / 哪次查询。

Q1会话树是不是拆成了「UI 界面 + 工具方法」两个插件？
✓ 确认：是，而且现在正以两个包在运行

UI 半 @local/dsh-session-tree v1.0.0：client.js 74.2 KB，占左栏 sidebar.workspaces 单席位（priority −100），提供树形会话、四态圆点、搜索、折叠、右键菜单等；同时注册只读 inspect provider SessionTree。
工具半 @local/dsh-session-tree-tools v1.0.0：纯宿主包，只提供一个 tree_send 工具（跨层级给任意 continuable 子会话发消息，含兄弟）。

证据（活体 + 文件）
  • cordis_inspect_list → client provider SessionTree 已注册（UI 半在运行）
  • cordis_inspect_query host Tool → 工具清单里有 tree_send（工具半在运行）
  • profile bundles 里两个名字各占一行，且 dependencies 是 link: 指向两个目录
  • UI 包 index.js 只有 23 行，注释明说「故意为空」
为什么要拆？（核心原因，和你要的合并直接相关）
  • DSH Loader 对宿主模块按包名缓存：改一个已装载包的 index.js，停用/启用、卸载重装、换入口文件路径三种方式都拿不到新代码，只能重启进程。
  • 但新包名没有缓存 → 普通 install_bundle 就能立即生效。所以 tree_send 被拆成新包，装完当场出现在工具列表里。
  • 顺带收益：重启后不会有两个包重复注册 tree_send。
  • 代价：两个包、两条测试/两份测试文件、两个版本号要维护。

03

合并专题：两个包 → 一个包，该走哪条路

切换看两种形态的实际文件布局。关键差异不在文件数量，而在 DSH Loader 的包名缓存——它决定了「合并后改宿主代码还能不能热更」。

合并值不值？一张表说清

维度两个包（现状开发态）一个包（已发布发布态）
安装/传播两条 install、两个版本要对齐一条 dsh plugin add orphiczhou/dsh-session-tree 装完
宿主改动能热更吗工具半是独立包，改它可换包名立即生效（UI 半本就能刷新页面生效）同包名已缓存 → 改 index.js 必须重启应用或再换包名
版本/测试维护2 个 package.json、2 套测试副本1 个版本号、3 份测试都在一个包里
注册冲突风险重启后两个包可能重复注册 tree_send（已用空 apply 规避）天然不存在
市场收录一条 listing 只能指一个仓库 → 双包没法上市场已收录（#6334 已合并）

⚠️ 本仓 packages/ 位于 profile 的 hmr.root 下（这就是 tree-engine 改完约 25 秒热更的原因）。把这层机制算进去，合并包如果放进本仓 packages/，宿主改动仍然可以热更——包名缓存的坑只在「仓外安装的包」上才无解。

方案 A：维持双态

开发双包 → 手动同步 → 发布单包

不动现状，发布前把 client.js/index.js 同步进 publish/ 并 bump 版本。风险最小，但每次发布要手工同步两处，容易漂移。

推荐

方案 B⁺：合并进本仓，单包 + HMR

一个包 · 放 packages/ · 发布就是 git push

把 publish/dsh-session-tree/ 迁进 packages/dsh-session-tree/（hmr.root 内）：一个包、一条 profile 行、一份测试；宿主改动照常热更；发布时把包内容推到公开仓库。唯一迁移动作 = profile 里停用两个 @local/* 包、改装单包。

方案 C：只保留发布单包

弃用本机开发双包

最省事但最痛：开发时改宿主半要重启应用（每次约十几秒到几十秒），历史包袱里「为什么拆」的教训会重演。不建议。
