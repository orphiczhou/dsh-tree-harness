一页看懂

1

A 已经把「图看不清」这个痛点解决了。做法是：未点亮的依赖虚线画在节点盒后面、点亮后压到最上层并加同色光晕；依赖边不再走贝塞尔直线，而是「障碍感知」的正交走线 + 圆角弧，绕开节点盒。已随 session-tree v1.8.3 交付，相关断言是 panel-render 的 V2-44..47。

2

B 是「加一个视图」，不是「改掉现在的图」。Hierarchy 视图保持现状（从属树 + 依赖虚线），新增 Dependency 视图：只把 dependencies 当边，按最长路径分层、同源/同目标边扇出、入度 ≥2 的节点加 join 标记。它借用的是 Flow Runs 的布局语言，不是它的语义。成本约 1.5 天，可逆，推荐作为下一步。

3

C 是「换一套世界观」，代价最高。把 parent 也当成边，整张图按 DAG 布局，只用一个视图。视觉上最像 Flow Runs，但会压平「谁派发谁」的层级（多层层级退化成并列），且现有按 parent 分层的断言要成片改口径。成本约 3 天，不建议，除非明确要求「两个面板视觉完全同构」。

01

先分清三套「关系」，这是所有取舍的根

树里的两种边，和 Flow Runs 里的边，语义完全不同；能不能「照抄」，取决于你愿不愿意丢掉其中一层信息。

体系边的含义有条件 / 数据吗能成环吗现在的画法
tree parent组织从属：谁派发了谁（严格树，每叶至多一个父）没有否（严格树）实线（品牌色），父 → 子
tree dependencies派发前置门：目标叶必须等前置叶结算后才能派发无数据传递、无条件表达式、无 join 语义引擎拦环，但可跨层反向指虚线，目标等前置
flow 引擎的边执行顺序 / 控制流：A 完成后才执行 B，可带 when 条件数据走变量池，不在边上；入边 ≥2 = join(all)否（DAG）折线 + 扇出偏移 + join 入边序号；未选中虚线，选中实线加粗
!

所以「把 tree 画成 flow 那种一张 DAG」不是纯视觉改造：要么把 parent 降格成普通边（层级消失），要么保留两套边在同一张图里（视觉噪音与语义混淆）。B 的做法是「分视图」，C 的做法是「合成一张」——这就是两者的根本差别。

证据：docs/operations/panel-v2/ROADMAP-relations-2026-11-17.md §0；flow 侧只读参照 spike/dsh-flow-plugin/client.js（布局与边绘制章节）。

02

A（已实施）：不换布局，只让关系「浮上来」

目标只有一个：虚线被节点盒挡住、点亮后仍被压住 —— 这两件事已经结束。

父 → 子（从属，实线） 目标等前置（依赖，虚线） 节点盒（位于边之上）
示意：D1-integrate 依赖 C1 / C2 / A1 三个前置；虚线从列间空道绕行，避免直穿节点盒。

四个实现要点

  • 边分两层：st-tr2-edges-back 在节点盒之前，st-tr2-edges-front 在之后——点亮边永远在最上层。
  • 障碍感知路由：depRoutePoints 区分 forward（列间竖直通道）/ same-column（列右侧通道）/ backward（反向，保留兜底曲线但强制进前层）。
  • 圆角弧：roundedPathOf 在折点用二次贝塞尔画圆角（半径 10），也就是你要的「弧形线」。
  • 点亮语义不变：选中节点相关边进前层 + 16% 同色光晕；无关边压到 0.12；悬浮仍显示「A is parent of B / B depends on A」。

它解决不了什么

  • 依赖密度高时（一棵树里依赖边接近叶数，或单节点入度 ≥3），仍需要「点了才看清」，因为主视图的列是按 parent 层级排的，不按依赖拓扑排。
  • 同列多条依赖只能靠列右侧 lane 扇出，极端情况下会形成「梳子」形长通道——可读但不直观。
  • 这正是 B 想补的洞，也是 C 想一次性换掉的根。

证据：ROADMAP §1；代码 packages/dsh-session-tree/client.js（depRoutePoints / roundedPathOf / TreeGraph）；断言 V2-44..47；实测 wave2 的 9 条依赖边在同列场景下画布由 484 扩到 578（v1.8.4 修复裁切）。

03

B（候选，推荐）：Hierarchy | Dependency 双视图

把「从属」和「依赖」拆成两个视角：需要组织关系时看树，需要判断「谁在等谁」时切到依赖视图——切换成本一次点击。

示意：同一批叶子换成「只画依赖」的 DAG 视图；D1 的三条前置在 level 1/2 一眼看清，不需要点选。

收益

  • 依赖密集的树（如 wave2 的 D1 等 3 个前置）在依赖视图里天然可读，不再依赖「点一下高亮」。
  • join 标记直接回答「它在等几个前置」，比数虚线快。
  • Hierarchy 视图完全不动 —— 从属语义不丢，属于纯增量。

成本与风险

  • 约 1.5 天：布局可复用现有分层算法（treeHierarchyOf 的 visited 防环逻辑），加视图切换与测试。
  • 风险 1：两套视图的认知负担 —— 缓解办法是视图切换按钮放在图区工具条，并在列头写清「按从属 / 按依赖」。
  • 风险 2：记住用户选择（需要持久化，localStorage 已封装且异常静默）。
  • 触发条件：单树依赖边 ≥ 叶数，或单节点入度 ≥3 的树占比变多。

证据：ROADMAP §2；flow 侧布局思路只读参照（最长路径分层 + 扇出偏移），不改变 tree 的任何契约。

04

C（候选，不推荐）：统一 flow 风格单图

一张图里同时画「从属」和「依赖」，用线型区分，整体按 DAG 布局。视觉最统一，但会牺牲层级直觉。

示意：parent 与依赖混在一张 DAG 里，线型能区分，但「谁派发了谁」不再由图本身表达，只能靠缩进/面包屑补。

收益

  • 视觉上与 Flow Runs 完全一致，一套图语言、一套交互习惯。
  • 如果未来 tree 与 flow 的关系进一步融合（例如树节点直接复用 flow 节点），这张图是自然的起点。

代价（这是不建议的原因）

  • 层级信息丢失：parent 本质是树，转 DAG 后多层从属退化为并列，直接削弱「根 → 指挥 → 执行」的直觉。
  • 回归面最大：现有 V2-6 / V2-7 / V2-9 / V2-16..20 等按 parent 分层、边数、尺寸的断言要成片改口径；约 3 天。
  • join 语义并不存在：tree 的 dependencies 没有 join 概念，强行画 join 会误导读者以为存在「全部前置通过才放行」的语义。
  • 触发条件：只有当你明确要求「两个面板视觉完全同构」且接受层级用其他形式表达时才考虑。

证据：ROADMAP §3；断言清单 V2-6/V2-7/V2-9/V2-16..20（parent 分层、边数、尺寸）。

06

怎么定：三个问题，一条推荐路径

选 B 推荐

当你满足其中任意一条：
① 经常需要判断「谁在等谁」；② 一棵树里依赖边密度接近叶数；③ 希望保留从属语义，同时把依赖看明白。

  • 依赖视图复用 treeHierarchyOf 的分层与防环，边按 dependencies 生成。
  • 同源/同目标边按 bend 扇出；入度 ≥2 画 join 圆标 + 数字。
  • 视图切换放图区工具条 + 记住选择；补 V2 断言与真机复验（约 1.5 天）。

选 C

只有当你明确说：「我不在乎图上是否还能看出层级，我要两个面板长得一模一样。」
否则不划算：成本翻倍、层级直觉丢失、旧断言成片改。

  • 先把层级信息改由缩进/面包屑承载（否则用户会失去「谁派发谁」）。
  • parent 与 dependencies 进同一 DAG 布局，线型 + 图例强区分。
  • 重写 V2-6/V2-7/V2-9/V2-16..20 等断言，并做真机回归（约 3 天）。
维持现状也可以：A 已经让「关系可见」不再依赖脑补。B 是增量，C 是换血——如果你倾向「先用起来再决定」，B 的风险最低；如果你想彻底统一两套图，再评估 C。

术语表（读图前先对齐）
  • leaf（叶）：树里的一个节点；可能是一个真实子会话，也可能只是容器。
  • root 容器：建树时自动生成的根叶，通常不接 done 事件，所以「树级状态」不能只看它。
  • 结算：叶的 runtime.state 进入成功/失败/超时等终态（不是 status 字段）。
  • 依赖闸：目标叶的所有 dependencies 结算后才能派发；无依赖时必须省略该键（空数组会被拒绝）。
  • join：flow 的语义（多条入边需全部完成）；tree 的 dependencies 没有 join 概念。
