B · 回执对来函的三处事实更正

更正 ①不存在 startContinuable▶
  • 宿主唯一启动入口 = startActivation(spec)（导出表 dsh-subagent/lib/index.js）；无 startContinuable / continueSession / resume。
  • 续接唯一原语 = subagents.sendMessage(sender, targetId, content, {signal}) → 非驻留目标走 coldResume。
  • 来函 §9 引用的 :1402/:1405 实为 assertSubagentMaxDepth / resolveChildDepth（均在 startLocal 内），不是第二个启动原语。
更正 ②dispose() ≠ 销毁会话▶
  • dispose() 只释放驻留（resident）+ 槽位；自然 settle 也走同一事务（槽位只算「运行中」，settle 即归还）。
  • 「不 dispose」既不会长期占名额，也不会自动保留活句柄。
  • 可靠形态只有：保留 sessionId → 之后冷恢复续接；前置 = sessionPersistence + sessionQuery + descriptor continuable + 目标子会话的直接父 Agent 存活。
  • 结论：来函 §4.2「保留 activation 句柄 + sendMessage」不可实现。
更正 ③深度配置由工具层注入▶
  • 宿主判据 resolveChildDepth：maxDepth !== void 0 才比较 → 不传 = 完全不比较 = 无上限。
  • 配置值 resolveMaxDepth(configured) 只把值算出来；注入 request.maxDepth 的是工具层（dsh-tool-subagent）。任何直呼 startActivation 的插件（flow、tree）必须自己 resolveMaxDepth(...) 后显式传。
  • 传入前有能力前置：provider 必须声明 capabilities.depthLimit，否则抛 UNSUPPORTED_CAPABILITY。
  • 本机 profile 实配 subagent.maxDepth: 5；被拒时抛 SubagentDepthError（无 .code，需按 name 识别）。
证据：RECEIPT-2026-11-13-from-flow-engine.md §2
