01

三句话看懂

What / Why / How —— 先建立一张心智图，再看细节。

01 · 是什么

DSH 上的「树形任务执行 Harness」

它不是单个插件，而是一组围绕树形分解的 DSH 包：执行层 tree-engine（9 个工具 + 竹节接力 + leaf 写面护栏）、会话树单包 session-tree（侧栏树 + tree_send + session_handoff）、自省层 introspect（self_spec）。

事实：根 README.md 包表；各包 package.json。

02 · 解决什么

长任务装不下、子会话看不见、分层后收不了口

单会话上下文有限；DSH 默认侧栏把 origin:'subagent' 的行藏起来，跨层/兄弟会话也没有内置通信路径；任务拆下去后，若没有账本、所有权与验收，就会「派了但不知道干到哪」。

事实：docs/architecture/session-handoff-2026-11-11.md §0.1；packages/dsh-session-tree/README.zh.md「为什么」。

03 · 怎么用

装两个 bundle → 新会话 → 一句话拆树

profile 里 link: 两个包并 pnpm install，对 bundle 做一次 disable→enable；新开会话即可看到 3 个 Skill。然后说「把这个任务拆成三层并派人做，验证通过再收口」，模型按 Skill 调工具。

事实：docs/guides/skills-usage.md §2–§4；D12 热更纪律。

一句话

树是账本，会话是执行体。任务分解成 leaf（账本行），每个 leaf 派一个真实 DSH 子会话去干；上下文到 42% 时引擎给同一个 leaf 换会话（竹节），到 50% 时任意会话可同层接替（handoff）——两种接力，都不丢任务书。

它不是什么

  • 不是新的 Agent 框架：没有自己的模型/运行时，只通过宿主 ctx 用 DSH 原生服务。
  • 不是自动项目管理器：模型仍是决策者；工具提供账本、闸门与可观测性。
  • 不是 npm 包：@orphiczhou/* 三个候选名在 registry 均 404，安装只走 Git / link:（D3）。
  • 不是零配置：装 bundle、重载宿主半、新开会话，三步缺一不可。

三个组件，两种状态

包版本状态一句话

02

5 分钟看懂：五个关键词 + 六步上手

不读源码也能建立正确预期；每张卡都给出「最容易误解的点」。

Keyword 01

DSH / bundle

DSH（DeepSeek Harness）是插件宿主。一个 bundle 由宿主半（index.js）和可选的客户端半（client.js）组成；cordis.patch.yml 决定它向 profile 贡献哪些行。

易误解：改了 index.js 保存后工具就变——不会，Loader 按包名缓存宿主模块，必须 disable→enable。

Keyword 02

会话树

把 DSH 左栏换成一棵可展开的树：每个会话下面挂它的 subagent 后代，任意深度；可按工作区分组、隐藏/恢复、搜索、按最近活动排序。

易误解：树只解决「看得见」；跨层发消息要靠 tree_send，接替要靠 session_handoff。

Keyword 03

leaf / 任务树

leaf 是账本里的一行（不是会话本身）：有 leaf_id、parent、role、runtime、events、verification。三层上限：root → commander → worker，worker 不能有子节点。

易误解：leaf 的 session_id 可以换（竹节/重派），账本不换。

Keyword 04

竹节 · 42%

worker 用 tree_report {action:"context", pct} 自报水位；pct ≥ 42 时引擎在同一个 leaf 上换一个新会话接手，旧会话先 interrupt，任务书/简报跟着走。

易误解：这是引擎自动的；不等于 50% 的会话交接，也不改 attempt。

Keyword 05

交接 · 50%

任意层会话在上下文约 50% 时，session_handoff 写一份 HANDOFF-*.md，并启动同层级接替会话：子会话→同父兄弟，根→新根（或父不活时降级根并标 degraded）。

易误解：交接不自动迁移 tree leaf 的 owner；接替会话要写 done，需先 set-session 重绑。

One screen

两种接力，先竹节后交接

竹节是引擎对 leaf 的换棒（更早、自动、保任务树）；交接是会话对会话的接替（更晚、手动/纪律、保会话层级）。

协调规则：先按竹节；已经 50% 还没等到竹节（链满 frozen、简报回收失败、已不是 running owner）→ 立即交接，并在 tree_report progress 留痕。

第一次用最容易误判的三件事

① 新会话直接 handoff 被 below-threshold 拒——这是预期，说明工具已挂上；想看完整路径加 force:true，只想写文件用 spawn:false（干跑不被阈值闸拦）。

② 5 分钟内第二次交接被 recent-handoff 拒——防重复闸，不是故障；确需立刻再写才用 force:true。

③ Skill 目录里没有三个 Skill——先确认是不是旧会话；目录只在会话启动时注入。

能力组合：三种典型用法

  • 单线长任务：root 建树 → 一个 commander → 一个 worker；worker 42% 竹节换会话，继续同一 leaf。
  • 并行多 worker：commander 建 3–6 个无依赖 worker，tree_dispatch 并行；tree_status harvest 收割，逐点 verify。
  • 三层验收：worker 自报 → commander 跑 tree_verify → 读 result.pass 再收口；root 最后 validate。

能力不是「越多越好」

tree-engine 的 tree_* 只负责任务账本与执行编排；会话生命周期（创建/fork/列表）仍走 DSH 原生 subagents，跨会话消息也可用内置 send_message（但只覆盖直接父子）。

发布面只有会话树是「公开镜像包」；tree-engine 与 introspect 随本仓公开、未单独发仓（见 docs/guides/publishing.md §1）。

事实：docs/guides/publishing.md §1；docs/architecture/tools-mapping.md §4。

为什么强调「零依赖」

三个包都不 import 任何 @deepseek-ai/* 包，只通过宿主 ctx 取服务。好处是测试不需要装载 DSH；代价是 DSH API 漂移时要自己补兼容层——RC2 的 startContinuable 移除就是一次实例，当前兼容层已运行但缺单测。
